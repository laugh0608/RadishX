## 内容核验方式

内容维护独立于功能扩展，不必等待新 Logo 或新截图。开始更新项目状态、公开入口或发布内容时，按项目核实：

| 字段 | 记录内容 |
| --- | --- |
| 核验对象 | 项目定位、维护状态、能力或具体入口 |
| 核验日期 | 实际完成该项核验的 Asia/Shanghai 日期 |
| 依据 | 所有者确认，或正式 README / 当前规划 / 发布说明的链接与版本、提交或日期 |
| 官网表达 | 短定位、当前状态、可用动作以及必要限制 |
| 未确认项 | 明确标为未核验，不从旧官网文案推断今天仍然成立 |

暂可将核验记录写入对应 feature 或开发日志；是否增加数据层字段随实际内容更新决定。本轮不伪造项目的核验日期，不自动建立定时抓取、监控或统计服务。

## SEO 输出评估

当前为 Vite 构建静态资源、单一 `index.html` 入口及客户端 History API 路由。当前 16 个正式页面（首页、十三个产品页、Mascot、About）没有独立 HTML 正文；未知路径按现有 fallback 返回入口，客户端再设置 `noindex`。

建议优先评估构建时为正式路由输出正文和独立 metadata，保持静态交付。方案需明确：

1. 页面数据、路由、sitemap 和 metadata 如何共享事实，避免生成后再次分叉。
2. 正常直达、刷新、尾斜杠、站内跳转及未知路径的输出与 HTTP 行为。
3. 原始 HTML 的 title、description、canonical、OG / Twitter 信息与浏览器最终状态一致。
4. 404 页面与资源路径的区分，缺失图片 / JS / CSS 不落到成功 HTML 外壳。
5. 是否增加依赖、如何构建、如何保持现有交互，以及如何回退。

本节没有选定新框架、预渲染工具或新的 Vercel 配置。当前客户端 `noindex` 是已有缓解，不能把未知路径返回成功外壳作为未来方案的验收目标；本轮也没有证据证明线上收录已受损。

参考：[Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)、[W3C 普通文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。

## 验证与完成标准

- 每个批次独立记录范围、实现结果和必要验证，不用历史全站截图或构建成功替代新改动的验证。
- 代码变化执行 `npm run build`；构建输出变化执行 `npm run check:local-release`；HTTP 与浏览器检查按 [开发规范](../development/standards.md) 执行。
- 页面改动至少覆盖 `1440x900` 和 `390x844`，共享主题或响应式改动再覆盖受影响主题与断点。
- 可复用浏览器脚本应进入受版本管理的验证目录；截图、运行汇总继续放 `output/`。不要把只存在于本地 artifact 的脚本称为仓库可复跑入口。
- 性能优化以真实加载证据为依据；本次包大小不等同于 LCP、CLS 或弱网性能。没有实际需要时不拆分大量小 chunk，不批量转码原图。
- 收口时逐项确认：访客能辨认用途、状态、可用入口；已选入批次的问题完成验证；未选方案明确保留为后续；本地完成与线上发布分别记录。
