# 10 规范扩展与版本兼容原则

本章只说明 family-ui 自身如何保持语义稳定。它不规定任何项目怎样引用、复制、接入或升级本规范，也不维护外部采用状态。

## 1. 扩展判断

新增视觉值或组件规则前，先判断它属于哪一层：

| 类型 | 归属 |
| --- | --- |
| 跨界面重复出现、语义稳定的基础值 | 可进入 family-ui token 或通用章节 |
| 只服务某种业务对象、平台壳或品牌活动的值 | 保留在使用方本地范围 |
| 仅为一次页面构图产生的尺寸或装饰 | 留在页面设计，不上升为通用 token |
| 来自外部参考图的表面特征 | 先提炼原则，不直接进入规范 |

扩展通用 token 时，应同时说明名称、语义、亮暗映射、典型用途、禁止用途和与既有 token 的差异。

## 2. 兼容原则

- token 名称表达语义，不绑定具体页面、技术栈或产品名称。
- 调整数值但不改变用途属于视觉变更；改变用途、删除 token 或合并语义属于破坏性变更。
- 新语义优先新增 token，不静默借用已有状态色或品牌色。
- deprecated token 应保留明确替代项和至少一个规范版本的过渡说明。
- 文档、`tokens.json` 与 `tokens.css` 在同一版本内必须保持一致。
- 具体实现是否采用新版本、怎样映射和何时升级，由实现方自行决定。

## 3. 品牌与操作色扩展

- `brand` 表达身份，`action` 表达可操作性，两者可以相同，也可以分离。
- 配色母板是参考集合，不对产品作主色或辅色分配。
- 自定义品牌色时，应同时定义 `brand-primary`、`brand-hover`、`brand-soft` 与 `text-on-brand`。
- 浅色品牌底不能默认搭配白字；必须根据实际对比度选择前景色。
- 状态色不因品牌调整而改变语义；若色相接近，必须通过文字、图标或形状区分。

## 4. 组件规则扩展

通用组件规则只描述跨界面稳定的形态、层级和可访问性要求。以下内容不进入本规范：

- 领域对象的数据结构与业务动作；
- 某一平台独有的窗口实现细节；
- 某一品牌活动的视觉包装；
- 某个页面为满足内容而产生的局部布局；
- 某个实现仓库的文件路径、类名、组件名或开发排期。

## 5. 参考资料扩展

新增参考 UI 时，应补充：

- 来源或可识别内容；
- 主要学习点；
- 明确不学的表面特征；
- 对应的通用规范章节；
- 版权和内部使用边界。

参考图数量不是目标。只有当新素材带来新的结构、状态、密度、平台或暗色观察价值时，才应加入索引；相似截图应避免重复堆积。

## 6. 版本记录

Changelog 只记录 family-ui 本身的规范变化，包括 token、章节、参考资料和兼容性说明。不得写入任何具体项目的采用状态、完成批次、迁移窗口或后续待办。
